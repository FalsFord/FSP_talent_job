# git-eval — микросервис оценки кода в git-репозитории

Принимает ссылку на репозиторий кандидата, клонирует его в изолированный временный каталог, прогоняет набор
анализаторов и возвращает оценку `0..1` с разбором по пунктам. Результат приходит в основной бэкенд подписанным
вебхуком (или забирается запросом). Сервис не знает ничего о ваших пользователях и базе: связь только через
`external_id` (у вас это `id` назначенного задания).

```
кандидат ──repo_url──► основной бэк ──POST /v1/evaluations──► git-eval (очередь)
                            ▲                                       │ clone → анализаторы → оценка
                            └────── вебхук (HMAC) ◄─────────────────┘
```

## Запуск

```bash
cp .env.example .env            # заполните GITEVAL_API_KEY и GITEVAL_WEBHOOK_SECRET
docker build -t git-eval .
docker run --rm -p 9000:9000 --env-file .env -v geval_data:/data git-eval
# документация API: http://localhost:9000/docs
```
Тесты ядра (без зависимостей, нужен только `git`): `python -m unittest discover -s tests -v`

Запускайте **один процесс** (`uvicorn` без `--workers`): очередь живёт в процессе, состояние в SQLite. После рестарта
прерванные задания и недоставленные вебхуки подбираются автоматически. Для нескольких реплик замените `Store` на Postgres
и вынесите воркер в отдельный процесс (интерфейс `Store` и `Worker` для этого изолирован).

## API

Все запросы, кроме `/healthz`, требуют заголовок `X-API-Key`.

**`POST /v1/evaluations`** → `202`
```json
{
  "external_id": "id-назначенного-задания",
  "repo_url": "https://github.com/owner/repo",
  "ref": "main",
  "language": "python",
  "rubric": [{"point": "Ключ идемпотентности", "keywords": ["idempotency", "uuid"], "min_hits": 1, "weight": 1.0}],
  "expected_author": "ivan",
  "weights": {"quality": 0.4},
  "callback_url": "http://api:8000/api/v1/internal/git-eval/callback"
}
```
Повторный запрос с теми же `(external_id, repo_url, ref)` возвращает уже существующую оценку (идемпотентно);
если прошлая попытка закончилась ошибкой — перезапускает её. Плохой URL даёт `422` сразу, а не после очереди.

**`GET /v1/evaluations/{id}`** → `{id, external_id, status, result, error, callback_status, ...}`,
`status`: `queued | running | done | failed`. Коды ошибок: `url_rejected`, `fetch_failed`, `empty_repo`, `internal`.

**Вебхук** (то, что получает основной бэкенд) — `POST` на `callback_url` с телом `{id, external_id, status, result, error}`
и заголовками `X-GitEval-Timestamp`, `X-GitEval-Signature` (`sha256=` + HMAC-SHA256 от `"<timestamp>.<тело>"`).
При не-2xx ответе — 5 повторов (1, 3, 10, 30, 90 с).

### Формат `result`
```json
{
  "score": 0.844, "verdict": "strong",
  "flags": ["single_commit", "secrets_committed", "author_mismatch", "no_source_code"],
  "summary": ["Не найдено подтверждения пункта: «Redis»", "Нет конфигурации CI"],
  "breakdown": {"quality": {"score": 1.0, "weight": 0.25, "metrics": {}, "findings": []}},
  "repo": {"url": "...", "ref": null, "head_sha": "…", "files": 12, "languages": {"python": 340}},
  "duration_s": 3.4
}
```
`verdict`: `strong` ≥ 0.75, `acceptable` ≥ 0.5, иначе `weak`. Это подсказка для человека, а не решение о найме.

## Как считается оценка

| Анализатор | Вес | Что проверяет |
|---|---|---|
| `quality` | 0.25 | Python: синтаксис (AST), длина функций, докстринги и типы, голые `except`, замечания `ruff`. Другие языки — только размер файлов, вес ×0.4 |
| `rubric` | 0.25 | Сколько пунктов рубрики задания подтверждено ключевыми словами в README и коде. Без рубрики не участвует |
| `structure` | 0.15 | README, тесты, CI, манифест зависимостей, `.gitignore`, мусор в git (venv, `.pyc`, `.env`) |
| `history` | 0.15 | Число коммитов, осмысленность сообщений, нет ли «одного гигантского коммита», разброс по времени, совпадение автора |
| `tests` | 0.15 | Доля тестового кода, наличие проверок (`assert`), опционально — реальный прогон в песочнице |
| `secrets` | 0.05 | Ключи, токены, приватные ключи, `.env` в репозитории. Значения секретов в результат не попадают |

Итог — взвешенное среднее по применимым анализаторам (веса перенормируются). Жёсткое ограничение: если в репозитории нет
исходного кода, оценка не выше 0.2. Падение одного анализатора не роняет остальные.

## Безопасность

Главный принцип: **чужой код не исполняется**. Всё, кроме опциональной песочницы, — статический анализ (чтение файлов,
`ast.parse`, `ruff`).

- URL: только `https`, хосты из белого списка, без логина/пароля в URL и нестандартных портов, путь строго `owner/repo`,
  хост должен резолвиться в публичный адрес (защита от SSRF). От DNS-rebinding полностью защищает только ограничение
  исходящего трафика контейнера на уровне сети — настройте его.
- `ref` проверяется регэкспом (нельзя передать `--upload-pack=…`).
- Клонирование: `core.hooksPath=/dev/null`, без сабмодулей и тегов, `GIT_TERMINAL_PROMPT=0`, без глобального конфига,
  разрешён только протокол https, лимиты по времени и размеру (убивается во время загрузки, а не после).
- Читаются только обычные файлы из `git ls-files`; симлинки пропускаются (нельзя «прочитать» `/etc/passwd` через репозиторий).
- Сервис не публикует порт наружу, доступ по `X-API-Key`; вебхук подписан HMAC и защищён от повторов по времени;
  `callback_url` должен совпадать с префиксами из `GITEVAL_CALLBACK_PREFIXES`.
- Работает от непривилегированного пользователя, временные каталоги удаляются после оценки.

### Песочница для запуска тестов (опционально, по умолчанию выключена)

Единственное место, где исполняется код кандидата. Включайте (`GITEVAL_SANDBOX_ENABLED=1`) только если выполнено всё:

1. Воркер, запускающий контейнеры, вынесен на отдельный хост или ВМ. Не давайте публичному процессу доступ к `docker.sock`: это эквивалент root на хосте.
2. Образ `GITEVAL_SANDBOX_IMAGE` собран заранее с `python` и `pytest` и типовыми библиотеками (сети внутри контейнера нет, зависимости из `requirements.txt` кандидата не установятся).
3. Контейнеры идут под усиленной изоляцией (gVisor или Kata), а не только под обычным runc.

Команда запуска собрана в `app/analyzers/sandbox.py` (`--network none`, read-only, `--cap-drop ALL`, лимиты памяти/CPU/процессов,
пользователь `nobody`). Здесь она проверена на уровне сборки команды; docker в окружении разработки не запускался.

## Что проверено и что нет

Проверено тестами (11, `tests/`): клонирование реальных локальных git-репозиториев, все анализаторы, итоговая оценка
«хорошего» и «плохого» проекта, флаги, непопадание значения секрета в результат, очередь и воркер, валидация URL и `ref`,
подпись вебхука. Не запускалось в окружении разработки: HTTP-слой на FastAPI и доставка вебхука (там не было сети и пакетов),
`ruff` (в тестах он отсутствовал, поэтому его вклад в `quality` не проверялся), клонирование с реального github.com, песочница.
Перед использованием прогоните сквозной сценарий из `integration/INTEGRATION.md`.

## Ограничения (важно для интерпретации)

- **Авторство не доказывается.** `expected_author` сверяет только подпись коммитов, а её легко подделать; форк чужого
  проекта с переписанной историей пройдёт. Для серьёзной проверки нужен сравнительный анализ (поиск совпадений с
  публичными репозиториями) и разбор решения на собеседовании.
- **Рубрика по ключевым словам обходится** вставкой слов в комментарий. Нужен ревью человека или LLM.
- Углублённый анализ есть только для Python; Java, Go, JS/TS получают грубую оценку.
- Приватные репозитории не поддерживаются (кандидат должен сделать репозиторий публичным или дать доступ другим способом).
- Мелкий клон (`depth=300`): для очень длинных историй считаются последние 300 коммитов.
