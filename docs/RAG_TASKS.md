# RAG-конвейер заданий и доработанная логика бэкенда

Документ описывает, что добавлено к исходному бэкенду, как устроен конвейер генерации тестовых заданий
(Python / Java / SQL × Intern…Lead), как использовать корпус Hexlet/ru-test-assignments и что **проверено, а что нет**.

## 1. Что сделано

| Блок | Содержание |
|---|---|
| RAG-конвейер заданий | корпус знаний → retrieval → генерация → валидация → выдача → проверка (`app/tasks/`) |
| Тестирование | экземпляры заданий по попыткам, дедлайн, автосохранение, анти-чит флаги, политика грейда (`app/services/assessment_service.py`, `app/domain/grade_policy.py`) |
| Подбор | категории → фильтры → pgvector ∪ навыки → ранг по силе профиля, объяснения, снимки подборок (`app/services/matching_service.py`, `app/domain/ranking.py`) |
| Приглашения | автомат статусов, зарплата «от–до» обязательна, лимиты, идемпотентность, `contact_reveals` — единственный источник права на контакты |
| Дополнительно (ТЗ) | вакансии и отклики, регулярные задания работодателя, уведомления, правила доверия к вакансиям (rule-based) |
| Платформа | единый формат ошибок, подтверждение e-mail (флаг), фоновое обслуживание, идемпотентные патчи схемы БД |

## 2. Схема RAG-конвейера

```
 Корпус знаний                         Запрос на тест / описание вакансии
 ├ builtin (авторские заметки)         (язык, грейд, специализация, текст потребности)
 └ Hexlet/ru-test-assignments                       │
        │ ingest: parse → classify → chunk → embed  ▼
        ▼                              ┌──────── Retrieval ────────┐
  knowledge_documents / knowledge_     │ вектор (pgvector, косинус) │
  chunks (pgvector + полнотекст)  ───► │ ∪ полнотекст (tsvector)    │
                                       │ → RRF → близость грейда    │
                                       │ → MMR (разнообразие)       │
                                       └─────────────┬──────────────┘
                                                     ▼  ContextPack: текст, источники, веса тем
                       ┌───────────── Blueprint (квоты по типам заданий) ─────────────┐
                       │ тема / «легенда» SQL / архетип «опишите подход» выбираются    │
                       │ с учётом контекста; недавно выданные генераторы — в конец    │
                       └──────────────┬───────────────────────────────────────────────┘
                                      ▼
        Генераторы (код, детерминированы по seed) + банк вопросов (task_items)
                                      ▼
                    Валидация (эталон воспроизводится, «мутанты» ловятся, схожесть с корпусом < 0.35)
                                      ▼
                  TaskInstance в попытке: условие (public) + ключ/тесты (private, не отдаются)
                                      ▼
               Проверка: SQL на 3 наборах данных · код в песочнице · варианты · рубрика
```

**Роль RAG честно.** Retrieval не «пишет» задание, а управляет выбором: какая предметная область для SQL
(магазин / доставка / банк / кино — по словам в найденном контексте и в описании вакансии), какие темы весомее
(`topic_hints`), какой архетип задачи «опишите подход» актуален. Сами условия, эталонные решения и скрытые тесты
создают проверяемые генераторы — это даёт сопоставимую сложность и объективную оценку (ТЗ отвергает «уникальные задания от
нейросети под каждого»). LLM — необязательный офлайн-инструмент: `POST /admin/tasks/drafts` готовит черновики вопросов
(статус `draft`, схема ответа проверяется строго, копирование корпуса отсекается), в тест они попадают только после ручного
утверждения.

## 3. Корпус Hexlet/ru-test-assignments

* Репозиторий — каталог Markdown-файлов с реальными тестовыми заданиями компаний (каталоги `java/`, `sql/`,
  `backend/python/…`, `analytics/` и др.), решений там нет. Лицензия репозитория на момент чтения — **AGPL-3.0**; тексты
  заданий принадлежат компаниям-авторам. **Проверьте лицензию и условия перед публикацией.**
* **Корпус не включён в репозиторий проекта** и не копируется в задания. Он подключается как локальная копия:
  ```
  git clone https://github.com/Hexlet/ru-test-assignments data/ru-test-assignments
  docker compose up -d --build            # entrypoint загрузит корпус, либо вручную:
  docker compose exec api python -m app.tasks.rag.ingest --path /data/ru-test-assignments
  ```
* Загрузка: `*.md` (кроме корня и скрытых каталогов) → очистка Markdown → классификация (язык по пути и тексту,
  грейд по ключевым словам, темы, компания) → чанки ~900 символов с перекрытием → эмбеддинги → БД. Документы без
  Python/Java/SQL пропускаются. Повторная загрузка идемпотентна (по хешу содержимого).
* Задания Hexlet — большие домашние проекты, поэтому их нельзя автопроверять за 40 минут. Они используются как
  **контекст** (какие архетипы задач актуальны) и для заданий «опишите подход» с **нашими** формулировками и рубриками
  (`approach_gen.py`). Условие задания всегда проверяется на схожесть с корпусом (3-граммы слов, порог 0.35).
* Без корпуса конвейер работает на встроенных заметках (`knowledge_builtin.py`).
* **Не проверено на реальной копии репозитория:** в среде разработки не было доступа в сеть для `git clone`; формат файлов
  изучен выборочно, парсер проверен на синтетическом образце. Первым делом запустите ingest и посмотрите
  `GET /api/v1/admin/knowledge/stats` и долю пропущенных документов.

## 4. Задания: языки, грейды, форматы

| Тип | Что проверяет | Как проверяется | Python | Java | SQL |
|---|---|---|---|---|---|
| `sql_query` | написать запрос | исполнение на 3 наборах данных (1 виден, 2 скрыты), SQLite; защита от «зашитых» ответов | — | — | 10 генераторов |
| `predict_output` | «что выведет код» | ответ вычислен выполнением доверенного шаблона; дистракторы — выводы мутированных шаблонов | 8 | 5 | — |
| `code_function` | написать функцию | скрытые тесты от seed, песочница (выключена по умолчанию) | 5 | 2 (нужен JDK) | — |
| `quiz_single/multi` | концепции | авторский банк, 45 вопросов (3 на язык×грейд) | + | + | + |
| `approach` | подход к решению | рубрика ключевых основ + ручная проверка (Senior/Lead) | + | + | + |

Покрытие по грейдам — число доступных генераторов (без / с включённым исполнением кода; включая «опишите подход» для Middle+):

| Язык | Intern | Junior | Middle | Senior | Lead |
|---|---|---|---|---|---|
| SQL | 2 | 3 | 6 | 6 | 3 |
| Python | 2 / 3 | 3 / 6 | 6 / 8 | 5 / 6 | 2 / 3 |
| Java | 2 / 3 | 3 / 4 | 4 / 5 | 2 / 3 | 1 / 1 |

Дополняют их вопросы банка (по 3 на язык и грейд). Для **Lead по Java и Python генерируемых заданий мало** (в основном
«опишите подход» и вопросы банка) — это самое слабое место покрытия.

**Квоты теста** (по умолчанию 16 заданий): 40 % исполняемые (SQL/код), 30 % «что выведет», 1 «опишите подход» для Middle+,
остальное — вопросы банка. Языки — по специализации (`backend`/`qa`/`devops`/`data`: Python + SQL) или переданные
в `languages`. Для специализаций без языков (`frontend`) API вернёт `NO_TASKS_FOR_SPECIALIZATION`, пока не передан `languages`.

## 5. Устойчивость к распространению заданий (требование ТЗ)

1. **Параметризация условия.** В заданиях-функциях константы и правила входят в формулировку и меняются по seed
   (например, «делятся на 3 или 7», политика кэша LRU/FIFO/MRU, порядок результата) — решение, написанное под один вариант,
   не проходит другой (проверено тестом `test_python_code_task_and_solution_not_transferable`).
2. **Данные SQL-заданий** и «легенда» (таблицы/термины) различны для каждой попытки; скрытые наборы ловят литералы.
3. **Вычисляемые ответы** для «что выведет»: ответ получается выполнением шаблона с параметрами конкретной попытки.
4. **Антиповтор:** недавно выданные генераторы уходят в конец очереди выбора; каждое прохождение — новый seed.
5. **Контроль экспозиции:** счётчики показов и средних баллов (`generator_stats`, `task_items`) — основа калибровки.
6. **Анти-чит:** события потери фокуса и слишком быстрое решение снижают «уверенность» результата (не наказание);
   при низкой уверенности `pass` невозможен (максимум `borderline`).

**Размер пространства вариантов** (число различных условий по 150 seed; чем меньше — тем легче собрать все варианты):
SQL — 150 (все генераторы); Python «что выведет» — 73–150; Java «что выведет» — 105–150;
задания-функции — **4–55** (group_first_letter 9, merge_intervals 8/4, top_k 12, LRU 6, sum_multiples 50–55).
Для функций защита слабее всего: у них мало вариантов, поэтому в выдаче доля таких заданий ограничена, а их стоит пополнять.

### Результаты синтетической валидации (`python -m app.tasks.simulation`)

Модель: скрытая способность кандидата, логистическая вероятность верного ответа; грейд-специалист справляется с заданиями
своего грейда на `margin` выше их средней сложности (допущение!). Используются реальные генераторы, сборка теста и проверка.
150 синтетических кандидатов (по 30 на грейд), тест 16 заданий, порог 0.70, margin 0.6:

| Метрика | Значение | Комментарий |
|---|---|---|
| Разделяющая способность (AUC, тест Middle: ≥Middle vs <Middle) | **0.944** | средняя доля баллов 0.83 vs 0.49 |
| Определение грейда ±1 (кандидат завышает заявку) | **0.98** | |
| Точное совпадение грейда | **0.55** | сильно зависит от допущения о margin (0.52–0.57 в сетке) |
| Повторяемость: корреляция двух прохождений | 0.46 | занижена из-за узкого разброса внутри грейда |
| Одинаковое решение при пересдаче | 0.67 | при margin 0.8 → 0.82 |

Чувствительность (24 кандидата на грейд, порог 0.70): число заданий 12 → 16 → 20 даёт AUC 0.92–0.95 → 0.96–0.97 → 0.95–0.96 и
корреляцию повторного прохождения 0.26–0.34 → 0.43–0.50 → 0.41–0.49: после ~16 заданий выигрыш мал, поэтому 16 — значение по умолчанию.

**Утечка ответов** (слабый кандидат получает ключ ответов чужой попытки): сгенерированные задания повторяются дословно
в **0.3 %** случаев, **статические вопросы банка — в 69 %**, прирост балла от шпаргалки **+15 п.п.** (до смещения квот
в пользу генерируемых заданий было +20 п.п.). Это **известная слабость**: банк мал (3 вопроса на язык×грейд). Меры:
пополнять банк (черновики через LLM с утверждением), параметризовать вопросы, держать долю статических вопросов низкой.

**Что эти цифры НЕ доказывают.** Это внутренняя согласованность механики на заданной модели, а не валидность на реальных
людях. Реальная калибровка (сложность пунктов, пороги, расстояние между грейдами — у соседних грейдов средние сложности
различаются всего на 0.5–0.9) требует реальных ответов; для этого собираются `generator_stats` и результаты попыток.

## 6. Политика грейда (ТЗ)

* Первичная категоризация: тест на заявленный грейд; `pass` (≥ 70 % и уверенность ≥ 0.5) → категория присвоена.
  Не прошёл → `next_step=try_lower`: сразу доступен тест на уровень ниже (без паузы).
* Грейд **никогда не понижается принудительно.** Смена подтверждённого грейда (вверх/вниз) — не чаще, чем раз в
  `GRADE_CHANGE_COOLDOWN_DAYS` (90) дней; отсчёт начинается с присвоения категории.
* Повтор теста на том же уровне — через 7 дней; просроченная попытка — пауза 24 часа.
* Подтверждение действует 180 дней, затем статус `stale`: вес в ранжировании линейно снижается до 0.7 за 90 дней, грейд не
  меняется; переподтверждение (`reattest`) продлевает срок и не считается сменой грейда.
* Еженедельный мини-тест (`purpose=micro`, 6 заданий) обновляет статус навыков; на грейд не влияет.

## 8. Выполнение кода кандидатов — важное предупреждение

Раннер (`app/tasks/runners/code_runner.py`) — эшелонированная защита (AST-фильтр, отдельный процесс, лимиты ресурсов,
ограниченные builtins), **но не полноценная песочница**: Python-изоляция принципиально обходима. Поэтому
`CODE_EXEC_ENABLED=false` по умолчанию, и задания `code_function` в выдачу не попадают. Для включения используйте
изолированный сервер без доступа к секретам и сети (в идеале — отдельный раннер в gVisor/nsjail/Firecracker). Для Java нужен JDK:
`docker compose build --build-arg WITH_JDK=1`. SQL-задания безопасны для включения всегда (SQLite в памяти, белый список
операций, лимиты времени/размера).

## 10. Что проверено и что нет

**Проверено выполнением:** 51 автотест ядра (генераторы, SQL-песочница и её запреты, запуск Python- и Java-кода, проверка
ответов, сборка теста, политика грейда, ранжирование, автомат приглашений, правила доверия, парсинг/классификация/RRF/MMR,
синтетическая валидация); валидация банка генераторов; на Python 3.12, SQLite 3.45, OpenJDK 21.

**Проверено только статически (код не запускался):** слой БД и API — модели, сервисы, роутеры. В среде не было Postgres,
FastAPI и SQLAlchemy. Выполнены: синтаксис, поиск неопределённых имён, сверка обращений `Модель.поле` с моделями, импорт всех
81 модулей с подставными библиотеками. **Первый запуск `docker compose up` может выявить ошибки в SQL/ORM-запросах** (особенно:
pgvector-запросы, `with_for_update`, патчи схемы, hnsw-индексы) — перед использованием пройдите сценарий вручную по Swagger.

**Не реализовано / ограничения:** фронтенд (в архиве его нет) — нужны экраны для новых типов заданий; интеграция с реальным
ФСП ID/реестром (интерфейс `FspProvider` и мок готовы); семантические эмбеддинги по умолчанию — хеш-эмбеддинг (не семантический),
для production включите `EMBEDDING_BACKEND=fastembed` (`requirements-ml.txt`, версии не зафиксированы и не проверялись);
настраиваемые этапы найма и интеграции с внешними ATS; JS/TS-задания для frontend; Alembic-миграции (вместо них — патчи схемы).

## 11. Совместимость с существующим фронтендом

* Тип вопроса `question_type` теперь — `quiz_single | quiz_multi | predict_output | sql_query | code_function | approach`.
  Варианты выбора — по-прежнему `options.choices`; для остальных типов данные в `public` (схема БД, предпросмотр данных, заготовка кода).
  Ответ: `{"answers": {"<id задания>": {"value": …}}}` (ключи `answer`/`selected` тоже принимаются).
* До принятия приглашения работодатель видит «Имя Ф.» (полное имя — после принятия или при `privacy.show_full_name`).
* Попытки, начатые прежней версией, считаются истёкшими через 2 часа; задания старого формата в них недоступны.
* Подтверждение e-mail выключено по умолчанию (ТЗ п.2.2(4) требует его — включите `REQUIRE_EMAIL_VERIFICATION=true` и добавьте
  страницу `/verify-email?token=…`); при включении `register` возвращает `verification_required=true` без токена.
* Демо-достижения ФСП теперь детерминированы по ID (0–3 события; часть ID без истории) — для проверки сценария «нет истории».
